# Schema v0.1 — Knowledge Graph del corpus regulatorio del BCRA

**Versión:** 0.1 (preliminar, para discusión con mentor)
**Fecha:** 2026-04-29

## Alcance

Este schema modela el **corpus regulatorio del BCRA** como knowledge graph (Capa 1 de la arquitectura). Específicamente representa la estructura interna de los Textos Ordenados, sus modificaciones a través de Comunicaciones, sus referencias cruzadas, y las categorías/condiciones operacionales que definen.

**No incluye en esta versión** la modelización de casos concretos (deudores, financiaciones, predicciones de scoring). Esa capa se contempla como sistema externo que consume este KG vía interfaces explícitas — ver sección "Interfaces con capa de caso" al final.

**Justificación de este alcance:** la contribución académica original de la tesis está en demostrar si modelar la estructura del corpus regulatorio como KG mejora la fidelidad y reduce alucinaciones de un sistema RAG, comparado contra RAG híbrido (denso + BM25 + reranking). Esa pregunta se responde con la Capa 1; la Capa 2 es ingeniería de aplicación que el banco resolvería con cualquier representación.

## Clases

### Clases estructurales (representan el documento)

**`bcra:TextoOrdenado`**
Documento consolidado emitido por el BCRA que agrupa una temática regulatoria.
Ejemplos: "Clasificación de Deudores", "Gestión Crediticia", "Grandes Exposiciones al Riesgo de Crédito", "Marco Normativo".

**`bcra:Comunicacion`**
Acto regulatorio que origina o modifica puntos de un Texto Ordenado.
Subclases por tipo:
- `bcra:ComunicacionA` — modificaciones normativas
- `bcra:ComunicacionB` — aclaraciones interpretativas
- `bcra:ComunicacionC` — fe de erratas

**`bcra:Punto`**
Unidad mínima de contenido normativo. Recursiva: un punto puede contener subpuntos.
Cubre lo que el documento llama Sección, Punto, Subpunto y Sub-subpunto (4-5 niveles de profundidad observados en el corpus).
Decisión deliberada: NO crear clases distintas por nivel jerárquico, porque la profundidad varía y el modelado por nivel se vuelve frágil.

### Clases semánticas (representan el contenido)

**`bcra:CategoriaClasificacion`**
Categorías operacionales definidas por la regulación.
Instancias en cartera comercial: SituacionNormal, EnObservacion, EnNegociacion, EnTratamientoEspecial, ConProblemas, ConAltoRiesgoInsolvencia, Irrecuperable.
Instancias en cartera consumo/vivienda: estructura paralela con leves diferencias.

**`bcra:Condicion`**
Requisito que debe cumplirse para que aplique una categoría o regla. Tiene atributos cuantitativos extraídos cuando son aplicables (ver decisión abierta #2 abajo).

**`bcra:Concepto`**
Conceptos técnicos definidos por la normativa (ej. "Capacidad de pago", "Flujo de fondos", "Responsabilidad Patrimonial Computable", "Cartera comercial", "Refinanciación").

**`bcra:SujetoObligado`**
Entidades a las que aplica la normativa.
Instancias: EntidadFinancieraGrupoA, EntidadFinancieraGrupoB, EntidadFinancieraGrupoC, FideicomisoFinanciero, ProveedorNoFinancieroCredito, SociedadGarantiaReciproca, ProveedorPlataformaCredito.

**`bcra:TipoFinanciacion`**
Categorías de operaciones de crédito.
Instancias: Comercial, Consumo, Vivienda, MiPyME, Microcredito.

## Relaciones

### Estructurales (jerarquía y composición)

| Predicado | Dominio | Rango | Descripción |
|---|---|---|---|
| `bcra:contienePunto` | Punto, TextoOrdenado | Punto | Composición jerárquica recursiva |
| `bcra:perteneceATO` | Punto | TextoOrdenado | Inverso convenience del anterior |

### Versionado y temporalidad

| Predicado | Dominio | Rango | Descripción |
|---|---|---|---|
| `bcra:vigenteSegun` | Punto | Comunicacion | Comunicación que actualmente da vigencia al punto |
| `bcra:originadoPor` | Punto | Comunicacion | Comunicación que creó el punto originalmente |
| `bcra:modificadoPor` | Punto | Comunicacion | Comunicaciones intermedias que modificaron el punto |
| `bcra:fechaVigencia` | Punto | xsd:date | Fecha desde la cual el punto está vigente |

**Nota de modelado**: el versionado es a nivel de Punto, NO a nivel de Texto Ordenado. Distintos puntos del mismo TO pueden tener distintas vigencias. Esto fue verificado en el corpus (páginas 4, 11, 12 del TO de Clasificación de Deudores muestran versiones distintas para puntos del mismo documento).

### Referencias entre normas

| Predicado | Dominio | Rango | Descripción |
|---|---|---|---|
| `bcra:referenciaInterna` | Punto | Punto | Referencia a otro punto del mismo TO |
| `bcra:referenciaExterna` | Punto | Punto | Referencia a punto de otro TO |
| `bcra:complementadaPor` | Punto | Punto | Relación de complementariedad explícita |
| `bcra:derogadaPor` | Punto | Punto | Derogación explícita |

### Aplicabilidad

| Predicado | Dominio | Rango | Descripción |
|---|---|---|---|
| `bcra:aplicaA` | Punto | SujetoObligado | El punto rige sobre este sujeto |
| `bcra:aplicaSobre` | Punto | TipoFinanciacion | El punto rige sobre este tipo de operación |

### Semánticas (contenido)

| Predicado | Dominio | Rango | Descripción |
|---|---|---|---|
| `bcra:defineCategoria` | Punto | CategoriaClasificacion | El punto define una categoría operacional |
| `bcra:exigeCondicion` | CategoriaClasificacion | Condicion | Categoría requiere que se cumpla la condición |
| `bcra:defineConcepto` | Punto | Concepto | El punto define un concepto técnico |
| `bcra:utilizaConcepto` | Punto | Concepto | El punto hace uso de un concepto definido |

## Literales y atributos

**Sobre `Punto`:**
- `rdfs:label` — identificador legible (ej. "Punto 6.5.3.2")
- `bcra:textoCompleto` — texto literal del punto
- `bcra:numeracion` — numeración estructurada (ej. "6.5.3.2")
- `bcra:nivel` — profundidad jerárquica (1=Sección, 2=Punto, 3=Subpunto, etc.)

**Sobre `Comunicacion`:**
- `rdfs:label` — identificador (ej. "A 7024")
- `bcra:numero` — número de comunicación
- `bcra:fechaEmision` — fecha de emisión
- `bcra:tipo` — A, B o C

**Sobre `Condicion`:**
- `bcra:descripcionTextual` — texto original de la condición
- `bcra:tipoUmbral` — categoría de umbral (días, porcentaje, monto)
- `bcra:valorMaximo` / `bcra:valorMinimo` — umbrales extraídos cuando aplica

## Decisiones abiertas (a discutir con Lucho)

### Decisión 1: Granularidad de las Condiciones

**Contexto:** las categorías de clasificación se definen como listas de condiciones que combinan texto descriptivo con valores cuantitativos embebidos. Ejemplo del Punto 6.5.3.2: *"Incurra en atrasos de hasta 180 días, con exclusión de los deudores comprendidos en el punto 6.5.2.2..."*.

**Opciones:**
- **A — Texto enriquecido:** modelar Condicion solo con su descripción textual. Simple, fiel al original, no requiere extracción semántica.
- **B — Estructurado:** extraer valores cuantitativos (180 días) como propiedades del nodo Condicion. Permite queries cuantitativas tipo "¿qué categorías permiten atrasos > 90 días?". Requiere pipeline de extracción robusta.
- **C — Híbrido:** texto enriquecido + extracción opcional cuando es trivial detectar el patrón.

**Inclinación inicial:** opción C, pero quiero discutir con Lucho qué priorizar para v1.

### Decisión 2: Modelado del versionado temporal

**Contexto:** un punto puede haber sido modificado múltiples veces a lo largo de los años (ej. punto 6.5.3.6 modificado por 6 Comunicaciones distintas).

**Opciones:**
- **A — Punto único con propiedades temporales:** un solo nodo `:Punto_6_5_3_6` con `:vigenteSegun :ComA8378` y propiedades de fecha. Simple, refleja el estado actual.
- **B — Versiones como nodos separados:** múltiples nodos `:Punto_6_5_3_6_v1`, `:Punto_6_5_3_6_v2` conectados por `:reemplazadaPor`. Permite queries históricas tipo "¿qué decía esta norma en 2015?".

**Inclinación inicial:** opción A para v1 (no necesitamos queries históricas para el caso de uso de scoring actual). Opción B queda como extensión futura.

### Decisión 3: Resolución de referencias externas

**Contexto:** los Textos Ordenados se referencian entre sí textualmente (ej. *"punto 1.1.3.2 de las normas sobre Gestión Crediticia"*). Para construir las aristas `:referenciaExterna` hay que resolver estas referencias programáticamente.

**Opciones:**
- **A — Pipeline LLM-based:** usar un LLM para extraer y resolver referencias durante la construcción del KG.
- **B — Reglas + LLM:** parsing por regex/reglas para casos predecibles, LLM solo para ambiguos.
- **C — Manual para piloto, automatizado después:** anotar manualmente las referencias del corpus piloto (3-4 TOs), automatizar para escalado posterior.

**Inclinación inicial:** opción C para v1 (manual para 3-4 TOs piloto). Define decisión clara de alcance.

### Decisión 4: Uso de FIBO o schema custom

**Contexto:** existe FIBO (Financial Industry Business Ontology), una ontología estándar para el dominio financiero. Podríamos basarnos en FIBO o construir un schema custom para BCRA.

**Opciones:**
- **A — FIBO como base:** mayor compatibilidad con sistemas externos, pero pesado (FIBO tiene miles de clases, mucho overkill para el alcance).
- **B — Schema custom (este v0.1):** liviano, específico al caso, más fácil de iterar.
- **C — Schema custom + alineación selectiva con FIBO:** modelado custom pero con `owl:sameAs` o equivalentes para términos clave.

**Inclinación inicial:** opción B para v1, opción C como extensión si se demuestra valor.

## Interfaces con capa de caso (Capa 2)

Aunque la Capa 2 no se modela en este v0.1, el schema deja explícitos los puntos de enganche para integración futura:

- Una `CategoriaClasificacion` puede ser asignada a un caso externo via predicado `:asignadaPor` (no modelado aquí, viviría en la capa de caso).
- Las `Condicion` con valores cuantitativos extraídos permiten matching automático con features de un caso (ej. `cliente.diasMora` matchea con `Condicion.valorMaximo` de la categoría candidata).
- Los `SujetoObligado` y `TipoFinanciacion` filtran qué subgrafo regulatorio aplica a un caso dado.
